# trading-contracts

Versioned, dependency-light [Pydantic v2](https://docs.pydantic.dev/) data
contracts shared by the research, simulation, model-serving and live-trading
repositories in this organization. The package defines the message shapes that
flow between those systems (market snapshots, prediction bundles, order and
asset intents, execution reports, deployment manifests), a canonical JSON
serialization with stable content hashing, and a compatibility checker that
validates whether a set of component manifests can be deployed together.

## Status

**ACTIVE — core library.** This is the contract authority for the trading
stack; five sibling repositories import it (see
[Consumers](#consumers-and-sibling-repositories)). Package version: **0.3.0**
(`pyproject.toml`).

## Role and non-responsibilities

**Owns**

- Data shape: strict Pydantic models that reject unknown fields
  ([`src/trading_contracts/contracts.py`](src/trading_contracts/contracts.py),
  [`src/trading_contracts/execution_v2.py`](src/trading_contracts/execution_v2.py),
  [`src/trading_contracts/config.py`](src/trading_contracts/config.py)).
- Canonical serialization and hashing: sorted-key UTF-8 JSON with non-finite
  numbers forbidden, `content_hash` producing `sha256:<hex>` digests
  ([`src/trading_contracts/canonical.py`](src/trading_contracts/canonical.py)).
- Contract versioning and deployment compatibility evaluation
  ([`src/trading_contracts/compatibility.py`](src/trading_contracts/compatibility.py)).

**Does not own**

- Model training, portfolio decisions, broker behavior, order routing,
  transport (HTTP/queues), persistence, or scheduling. Those live in the
  consumer repositories.

## Architecture

Pure library, `src/` layout, no console scripts and no plugin entry points.

| Module | Contents |
|---|---|
| [`contracts.py`](src/trading_contracts/contracts.py) | Core envelope + models: `MarketSnapshot`, `PredictionBundle`, `DecisionContext`, `AssetIntent`, `PortfolioIntent`, `OrderIntent`, `ExecutionReport`, `AssetDefinition`, `CellDefinition`, `MetricCatalog`, `ComponentManifest`, `DeploymentManifest`, producer identity and artifact references |
| [`execution_v2.py`](src/trading_contracts/execution_v2.py) | Broker-grade execution contracts: `OrderIntentV2` with `ProtectiveBracket` and `RiskEnvelope`, `ExecutionReportV2`, `BrokerCapabilitySnapshot`, `OwnerCommand`, legal order-state transitions (`LEGAL_TRANSITIONS`, `is_legal_transition`, `protection_covers_filled`) |
| [`config.py`](src/trading_contracts/config.py) | `TradingExperimentConfig`, `TradingRuntimeOverlay`, `CandidateGenomePatch` |
| [`canonical.py`](src/trading_contracts/canonical.py) | `canonical_data`, `canonical_json`, `canonical_json_bytes`, `content_hash` |
| [`compatibility.py`](src/trading_contracts/compatibility.py) | `contract_family_major`, `contract_versions_compatible`, `evaluate_deployment_compatibility`, `CompatibilityReport` |

Supporting assets:

- [`schemas/`](schemas/) — 19 exported JSON Schemas, one per public model,
  regenerated by [`scripts/export_schemas.py`](scripts/export_schemas.py).
- [`examples/`](examples/) — canonical example documents (smoke intents,
  manifests, metric catalog, runtime overlay) built by
  [`scripts/build_contract_examples.py`](scripts/build_contract_examples.py).
- [`tests/`](tests/) — contract, config, execution-v2 and compatibility tests.

## Compatibility policy

Contract versions are strings of the form `family.vN` (for example
`execution.v2`), validated by
[`compatibility.py`](src/trading_contracts/compatibility.py). Two versions are
compatible when family **and** major number match exactly:

```python
from trading_contracts import contract_versions_compatible, content_hash

contract_versions_compatible("execution.v2", "execution.v2")  # True
contract_versions_compatible("execution.v1", "execution.v2")  # False
content_hash({"b": 1, "a": [1, 2, 3]})  # "sha256:5bf78e9b6650ca72..."
```

(Verified with Python 3.12.13; output as shown.)

`evaluate_deployment_compatibility` checks a `DeploymentManifest` against a
set of `ComponentManifest`s: required roles present, role keys consistent,
training cutoffs not in the future of the deployment cutoff, bound component
hashes matching manifest content hashes, and producer/consumer contract edges
satisfied. It returns a structured `CompatibilityReport` instead of raising.

## Artifacts and reproducibility

- `schemas/` and `examples/` are generated, committed artifacts; regenerate
  them with the two scripts in [`scripts/`](scripts/) after model changes and
  commit the diff. Both scripts are deterministic (sorted keys, fixed example
  timestamps), so a clean tree after regeneration means the committed
  artifacts match the code.
- Persisted contracts require timezone-aware timestamps, stable
  `object_id`/`trace_id` identifiers and producer identity, which is what
  makes content hashes reproducible across services.

## Safety and security

This package contains no credentials, no network code and no broker
connectivity. It describes messages for trading systems that currently run in
**simulation and paper/demo venues only**; nothing in this repository is
financial advice.

## Limitations

- **Version skew at consumers.** The package is `0.3.0`, but consumers that
  declare the dependency pin only `trading-contracts>=0.1.0`, and two
  consumers (lts, gym-fx) import it without declaring it in their packaging
  metadata. Editable-install metadata in a long-lived environment can also
  lag the tree (an installed metadata version of `0.1.0` against this `0.3.0`
  tree was observed). Treat the git tree, not installer metadata, as the
  authority.
- A committed `build/` directory from an old bdist run is present; it is not
  the source of truth — `src/trading_contracts/` is.
- No LICENSE, CONTRIBUTING or CITATION file currently exists in this
  repository.
